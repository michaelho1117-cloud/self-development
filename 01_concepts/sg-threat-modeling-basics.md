## Goal

小さなシステムを見て、**守るもの（資産）→ 何が起きうるか（脅威）→ 何で抑えるか（対策）** を1枚の対応図として説明でき、対策を「なんとなくセキュア」ではなく脅威に紐づけて選ぶ。

## Core ideas

### 1. 脅威モデリング = 「攻撃手順の暗記」ではなく「対応づけの設計」

SG で最初に押さえるのは、ツール名や exploit の羅列ではない。**何を守るか決めずに対策を並べない**こと。

Feynman 一言: *「鍵をかける前に、何が入っている箱かを言え。」*

最小の3列:

| 資産 (Asset) | 脅威 (Threat) | 対策 (Control / Mitigation) |
|--------------|---------------|-----------------------------|
| 守る価値のあるもの | 資産を損ねる起きうる出来事 | 脅威の発生・影響・検知を抑える仕組み |

- 資産が曖昧だと、対策はファッションになる（「とりあえず WAF」「とりあえず暗号化」）。
- 脅威が資産に刺さっていないと、対策の優先順位が付かない。
- 対策は脅威の**どの段**（発生防止 / 影響低減 / 検知・復旧）を狙うかを一言で言えると強い。

### 2. 資産は「データ・機能・信頼」のどれかで言い切る

試験・実務とも、資産を「サーバ」とだけ書くと薄い。次の軸で言い換える:

- **機密性 (C)** — 漏れて困るもの（個人情報、認証情報、鍵）
- **完全性 (I)** — 改ざんされると困るもの（取引記録、設定、署名済み成果物）
- **可用性 (A)** — 止まると困るもの（決済 API、認証サービス、監視）

Feynman 一言: *資産ラベルは「箱の名前」より「壊れ方の種類」。*

例: 「顧客 DB」→ 顧客 PII の**機密**、注文履歴の**完全性**、照会 API の**可用性**、と分解すると脅威が書きやすい。

### 3. 脅威は「誰が・何を・どう損なうか」の短文

フレームワーク名（STRIDE 等）は後から地図として使う。入門では一文で足りる:

- Spoofing（なりすまし）/ Tampering（改ざん）/ Repudiation（否認）/
  Information disclosure（情報漏えい）/ Denial of service（妨害）/
  Elevation of privilege（権限昇格）

覚え方の芯: **脅威カテゴリは資産の壊れ方の分類**。カテゴリを埋めることが目的ではない。

対比の一言: *「SQL インジェクション」は攻撃手法の例。脅威モデリングの行には、まず「注文データの完全性が壊れる」と書く。*

### 4. 対策は脅威に紐づく（Defense-in-depth の芽）

良い対策行の形:

1. どの脅威行を抑えるか（参照）
2. 予防 / 低減 / 検知のどれか（役割）
3. 残存リスクは何か（一言）

悪い例: 「多要素認証を入れる」（どの資産・どの脅威の行か不明）。  
良い例: 「管理者コンソールへのなりすまし → MFA + 管理面のネットワーク制限（予防）／失敗ログイン検知（検知）。端末盗難時のセッション窃取は残る。」

境界防御だけの対策表は、内部脅威やサプライチェーンを落とす。ゼロトラストやログ設計は後続トピックへ橋を架ける。

### 5. 1枚図の作り方（試験・机上演習用）

1. 範囲を決める（例: 「社内向け顧客照会 Web」だけ。全世界の脅威を書かない）。
2. 資産を 3〜5 個、C/I/A つきで列挙。
3. 各資産に脅威を 1〜2 文（カテゴリ名は任意）。
4. 各脅威に対策を 1 つ以上。**対策なしの脅威**は意図的に残すか、受け入れと書く。
5. 「この対策はどの脅威行を消す／薄くするか」を矢印または ID で結ぶ。

## Why it matters (exam / practice)

- SG のセキュア設計・リスク議論の共通言語。ガバナンス（何を守るか）と技術対策（どう守るか）の接続点。
- 午後試験のシナリオで「まず何を洗い出すか」の初手になる。
- 後続の OWASP 理解・暗号利用判断・インシデント対応は、この3列がないと優先度がぶれる。

## Common confusions

- **対策から書き始める** — 「暗号化すれば安心」は、漏えい脅威への対策候補に過ぎない。改ざんや停止には別の行が要る。
- **資産 = ホスト名** — ホストは器。中のデータの C/I/A と、提供機能の可用性を分けて書く。
- **脅威 = 脆弱性名のリスト** — CVE や OWASP 項目は「起き方の候補」。モデルの行はビジネス／システムの損ね方。
- **全部をゼロにする幻想** — 残存リスクを書かないモデルは優先順位が付けられない。受け入れた脅威も1行で残す。

## Socratic checks (fill after claiming understanding)

1. **Why not X?** 「全 API を TLS で保護した」だけで脅威モデル完了と言えるか。TLS が主に抑える脅威と、抑えない脅威を資産つきで挙げよ。
2. **Edge case / first principles?** 資産が「公開マーケティング用静的サイト」だけのとき、顧客 PII システムと同じ対策チェックリストをそのまま適用すべきか。何が変わり、何が残るか。
